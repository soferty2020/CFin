## B: distinct-date entries and timing

Synthetic prior cell: Oct 03 / category A / income: IDs `aaaaaaa1...`, `aaaaaaa2...`, amounts 100.00 and 25.50. New cell: Oct 17 / category B / expense: ID `aaaaaaa6...`, amount 6.00. Browser opens prior cell, closes it, and opens new cell. The heading immediately becomes `Демо-статья B · Расход · 2026-10-17`, while stale total 125.5 and two prior entries, complete with Edit/Delete buttons, remain. No loading indicator appears in sampled modal text. At 75 ms injected delay, first sampled stale view occurred ~14 ms after click; correct new total 6 and its one row appeared by ~115 ms. At 1200 ms delay, stale view occurred ~13 ms after click, correct view by ~1231 ms. These are discrete observations; actual transition may lie between samples, not an exact continuous visible duration. Proxy timestamps for each GET (start, HTTP response headers, end and status) are in `timeline.json`; the app modal shows old state until the new response resolves. The **zero-added-delay exploratory** run did not sample stale rows, so this test does not claim reproducibility on every fast loopback switch or production latency.

At both 75 and 1200 ms, CDP clicked **Edit** on the first stale row while the new-cell heading was visible: amount input became 100.00 and form changed to `Изменение записи`. It also clicked **Delete** on that stale row: confirmation read `Удалить запись 100 ₽?`. Delete was canceled; edit was never saved. No PATCH/DELETE/POST was sent; before/after API reads verified both synthetic date sets unchanged. The observed consequence is that controls for another date are actionable in the misleading new-date modal, and would target that old entry if subsequently confirmed/saved; actual deletion, persisted edit, behavior after a delayed response while editing, and production user impact were not tested. `server-snapshot/frontend/src/main.tsx:18-21,26,31,36` keeps `entries` as independent state, sets `cell` and form fields before awaiting `/entries`, never clears old entries or sets a loading guard, and `edit`/`delEntry` consume the row supplied by the stale list. A second race is possible because there is no request identity/cancellation for overlapping `openCell` calls; not independently demonstrated here.
