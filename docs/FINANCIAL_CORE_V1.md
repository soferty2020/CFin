# Financial core v1 — local Issue #4 implementation (not deployed)

All entered operations are facts under the Owner's policy. A row changes an account once on its stored date whether past, today, or next month. A missed payment must be manually moved or deleted; no overdue filter, rollover or execution-status column exists. Server date is calculated in Asia/Novosibirsk. Yesterday's end of day is `current`; today and later are forecast by date, with today's movement shown separately and counted once. These names describe the view, not whether a bank independently verified execution.

## Account accounting and certification

For each account, an operator manually attests a signed `numeric(18,2)` opening at the START of an effective date with a reason and revision. This is never inferred from the undated `accounts.opening_balance`, including stored zero. `first_activation` means that prior nonexistence and absence of prior funds were explicitly checked. An account without a baseline remains unknown, not zero. An explicit later opening resets the carry on its date; the API exposes the signed gap to the prior end-of-day result. An unresolved gap makes the trusted `balance` null, while `conditionalBalance` exposes the uncertified scenario. Transfers are one standalone row with two simultaneous opposing account legs and net zero company movement. Legacy paired legs contribute as existing entries once; a reviewed sidecar links them but adds no second implicit transfer. No linked financial row can be edited/deleted until the link is removed. NULL-account and unreviewed legacy rows retain their original bytes and make the resulting totals incomplete until human review. A newly created account changes the roster fingerprint, invalidating prior inventory attestation. Inactive accounts with holdings remain counted.

Each day uses all dated account movements. Company balance is solely the exact sum of the effective account balances, never an independent company opening. `balance:null` plus `reasons` means incomplete; `conditionalBalance` is not a trusted total. The calendar displays the pinned-base full-month layout with exactly two financial rows directly below the date headers: trusted start (`balance - movement` in BigInt cents) and trusted end of day. Category income/expense cells remain manually editable, including weekends; no group/subgroup subtotals or cash-gap placeholder are shown. An unfetched month and incomplete certified balances are not zero. Baseline, inventory, transfer, and review controls are on the existing Accounts page, not in a new calendar panel. Changing a dated entry recalculates from a new read snapshot; there is no persisted daily aggregate. Monetary balance arithmetic and UI formatting use BigInt cents and decimal strings, not IEEE floating point; legacy `/api/balances` remains backwards compatible but must not be presented as the new certified current balance. A separate month-specific `/api/daily-balances` response contains `asOfDate`, `timeZone`, `current`, a separately calculated `today` snapshot, `todayMovement`, selected-month `days`, per-account segment/reset details, and review queues. The today summary remains independent of the selected calendar month. If an operation on a given day has no allocated account, that day's all-operations `movement` (and `todayMovement` when applicable) is null with `movementComplete:false`; per-account movement is only conditional, not an all-operations figure. Earlier unresolved rows still invalidate later balances, but do not falsely invalidate a later day's movement without a new unallocated row. Async refresh responses/errors are guarded against superseding navigation requests. Its range is bounded to years 2000–2100, a 3660-day span, at most 1000 accounts and 10000 entries/reviews/transfers/baselines per snapshot; otherwise it fails closed.

## Schema and endpoints

`db/init.sql` creates the new tables on **fresh** installations; `db/migrations/002_financial_core.sql` is additive for existing databases. Never re-run `init.sql` over a retained database. Nothing has been migrated or deployed by this task. Fresh-init/migration replay, direction guards and concurrent category edits passed on isolated synthetic PostgreSQL 16; this does not verify a retained-database upgrade or production behavior. Before any later production migration: separately authorized operator, verified backup/restore plan, migration review, and independent deployment gate. Neither rollback nor deletion of retained data is authorized here.

All new routes require the existing session cookie and same-origin mutation protection. `GET /api/daily-balances?month=YYYY-MM`, `GET /api/account-baselines`, CAS `PUT /api/account-baselines/:accountId/:date` (`revision:0` for create), `POST /api/financial-inventory/attest`, `POST /api/transfers`, `PATCH/DELETE /api/transfers/:id` (manual correction of one atomic move), `POST /api/entries/:id/review` (manual operating/account assignment), `POST /api/legacy-transfers` (review matching opposite legs), and `DELETE /api/legacy-transfers/:id` (unlink for repair). Existing `/api/calendar`, `/api/balances`, and entry POST/PATCH payloads remain accepted. Review decisions are invalidated in calculations when original date, category, direction, amount or account changes. An old-client write without explicit manual review is accepted but does not certify the new balance until checked.

## Local acceptance scenario

Bank attested 100.00 at yesterday morning, cash explicitly first effective today at 25.00. Today bank expense 10.00, cash receipt 2.00: yesterday current 100.00; today's movement -8.00; today company forecast 117.00. Today bank→cash transfer 7.00: bank 83.00 and cash 34.00; company stays 117.00. Tomorrow cash receipt 3.00: 120.00. Tomorrow bank reset at 120.00 against previous 90.00 (without the transfer) yields delta +30.00 and incomplete certified total until reconciled. Future-month expense reduces forecast on its date and stays there until user moves/deletes it. The exact-cent case `90071992547409.93 + 0.01` produces `90071992547409.94`.

## Remaining verification / limitations

End-to-end HTTP entry-write transactions against real PostgreSQL, retained-database migration, transfer concurrency, actual browser usability and production parity remain **UNVERIFIED** unless independently tested. Synthetic PostgreSQL fresh-init/migration replay and category-concurrency tests passed; synthetic route tests cover accountless legacy writes and explicit-account sidecars, not real PG HTTP writes. Account inventory attestation confirms current IDs, not bank balances. A manual `reconciled` declaration does not itself prove external reconciliation. Legacy reviewing is explicit and potentially labor-intensive; no automated matching is attempted. Legacy `/api/balances` does not include openings and must not be relied on for actual cash. This local snapshot is not proof of current production state.
