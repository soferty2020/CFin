# PROC-P01-P16 v1.3 — локальный регламент CFin

## 1. Статус, приоритет и запреты
Документ организует *только* операции внутри явного Owner START и подтверждённого task scope. Отдельное одобрение применения самого документа и SOUL обязательно; текст предложения не является START новой Issue и не меняет технических прав. При конфликте с действующим более строгим SOUL/Owner scope остановиться. Только подтверждённый уполномоченный Lead организует; наименование Global Lead/Tester не является подтверждением операционной роли. Только отдельно уполномоченный Global Lead может писать обычную Coordination Card ровно из канонических 14 полей; Protected Card opt-in и N-06 affected egress — NO-GO, runtime enforcement — NO-GO/UNVERIFIED, IP conformance — UNVERIFIED, R02 T01–T10 не разрешены. Никакого обхода средствами профиля. Reviewer read-only (без файлов, Git state, БД, external writes). Lead не реализует код, не проводит независимый Review и не меняет проектные файлы/профили. Programmer не меняет production и чужие worktrees. Любая более узкая граница Owner или инструмента преобладает.

## 2. Одна постановка и binding P01/P07/P09/P16
Для *новой*, а не автоматически взятой из backlog Issue Owner явно даёт START: идентификатор задачи, цель и критерии, локальный корень worktrees, полный base commit SHA, разрешённые файлы/паттерны с трактовкой исключений, допустимые локальные действия, запреты и условия pilot dispatch. Одно такое заявление покрывает создание обычных локальных карточек, назначение исполнителей, реализацию, независимую проверку, Review, rework и отчёт без пошагового повторного разрешения при неизменном scope. Если START, pilot dispatch или границы отсутствуют — остановить соответствующую работу и уточнить Owner; нельзя вывести START из backlog/этого текста. До начала Lead фиксирует `критерий → сценарий → среда → evidence → результат/ограничение`, различает acceptance всей Issue, отдельной подзадачи и PR; неоднозначный UX уточняет заранее. До любого deploy согласовать пункты и достаточную среду каждого smoke; ответ Owner связать с чеклистом, уточнять лишь оставшееся неизвестным, не добавлять задним числом обязательную production write-проверку без исходного требования/конкретного риска. Наблюдение сохранности выбранных данных не равно аудиту всей БД. CI или неиспытанный rollback отмечать отдельным риском, а не произвольным новым критерием FAIL.

Owner может явно делегировать Lead *выбор* нового отдельного worktree и branch только внутри данного root по процедуре ниже; иначе нужны прямо одобренные Owner точные worktree+branch. Делегация не расширяет список файлов, base или внешние права. Lead записывает task binding: Owner START reference; canonical absolute root and worktree path; branch name; exact full base SHA; origin identity и ожидаемый remote-tracking/base ref; allowed paths; проверку отсутствия target path/ref и коллизий с `git worktree list`, branch refs и карточками; assignee и идентификатор задачи. Согласовать порядок при конкурирующих карточках: один binding на задачу, уникальные path/branch, никакого переиспользования чужого незавершённого worktree. Создание worktree делает лишь роль с отдельным правом локальной записи, не Lead, если Lead:11 остаётся. Перед созданием сверить origin URL/ref, HEAD base и статус исходного checkout в read-only режиме; никакого fetch без соответствующего разрешения. После создания и перед каждым write Programmer повторно сверяет cwd/реальный worktree, branch, HEAD/base (ожидаемые изменения HEAD после локального commit документируются), origin, working-tree status (включая untracked) и разрешённые пути; неизвестные/лишние изменения или drift — стоп. Не менять main checkout, чужие ветки/worktrees, shared Git config или профили. Локальный commit — лишь по явно разрешённому локальному scope/этапу, с проверкой staged diff; START сам по себе commit не разрешает, если это действие не названо.

## 3. Матрица полномочий P08
Действие | ответственный | gate. Локальные карточки/dispatch: уполномоченный Lead после Owner START, разрешённого pilot dispatch и проверки scope/assignee; это не право на защищённые Coordination Cards. Worktree/branch: назначает Lead только если Owner *явно* делегировал процедуру §2 (иначе Owner задаёт конкретную пару), создаёт уполномоченный на локальную запись исполнитель, Programmer сверяет binding. Локальная реализация/evidence/rework: Programmer внутри задания и allowed files после binding. Локальный commit: уполномоченный исполнитель лишь если Owner scope включает этот этап, после staged verification; не утверждение push. Независимый read-only Review: отдельный Reviewer, не автор реализации; сам файлы не пишет. Независимый *file-producing* rerun: отдельно названный и назначенный в рамках того же START исполнитель, **не автор реализации**, с подтверждённым SOUL, инструментальным допуском, отдельным местом и разрешённой средой; назначение имени Tester само по себе не допуск. Если его нет или повтор не состоялся — ось rerun UNVERIFIED, а не фиктивный PASS. Push, публикация draft PR и перевод ready: каждый соответствующий конкретный внешний этап отдельно разрешает Owner (не вытекать из START/commit/Review). MERGE: отдельное Owner MERGE. DEPLOY: отдельное Owner DEPLOY и допустимый production-оператор; Programmer напрямую production не меняет. ROLLBACK: отдельное применимое Owner решение, кроме заранее конкретно одобренной аварийной процедуры (если таковая реально подтверждена); не выводить его из deploy. CLOSE: отдельное Owner CLOSE с проверкой критериев. Удаление/cleanup worktree, branch, backup или evidence: отдельно разрешённый адресный scope, не автоматический шаг после CLOSE. Внешние записи вообще запрещены без применимого Owner gate; read-back фактического результата после каждой разрешённой внешней записи обязателен. Эти назначения описывают желаемый процесс, не удостоверяют наличия Global Lead/Tester и не заменяют технический контроль.

## 4. Инструменты, отказ и UNKNOWN P02/P03/P04
Чтение через доступные штатные read_file/search_files и адресные Git read-only queries; проверки значимых аспектов отдельно (`node --check` если применимо, отдельные `git status`, `git diff`, `git diff --check`, штатный hash), каждая с названием, точной командой/инструментом, exit code и результатом. Не смешивать несколько проверок в неразделимый shell-вызов. Проверить доступность инструмента, не считать правило одобрения ресурса разрешением запрещённого способа. При отказе зафиксировать буквальный текст, операцию, границу (отказ конкретного метода либо запрет ресурса/политики), зависимые проверки. Независимые разрешённые этапы можно продолжить; запрет ресурса не обходить сменой интерпретатора, переносом скрипта или изменением approval-настроек. Если запрет/новое право неясны — Owner, без домыслов. После неоднозначной внешней записи статус UNKNOWN: остановить зависимые действия, адресный read-back фактического target, сопоставить identity/состояние с запросом, сообщить расхождения, никаких слепых повторов. Не присваивать PASS отклонённым/неисполненным подкомандам.

## 5. Evidence, воспроизводимость, независимость P05/P06/P11/P12/P13/P14/P15
До запуска определить стойкое разрешённое хранилище, fixture, snapshot кода (HEAD и hash незакоммиченного diff), локальное время/timezone и версии инструментов. Сохранять точные команды, raw stdout/stderr, exit, структурированный результат, необходимые изображения, hash/manifest и привязку к среде/сценарию. Без секретов, реальных финансовых данных, browser profiles и ненужных scratch файлов. Исходный и независимый наборы не перезаписывать; хранение независимого набора обеспечивает только отдельно уполномоченный исполнитель §3. Проверять наличие итогового raw log именно в передаваемом пакете (ignored `run.log` не включится автоматически); допустим сохранённый разрешённый текстовый файл либо отдельное долговечное вложение с hash+ссылкой. Exploratory logs не выдавать за финальный PASS. Snapshot исторического прогона не переписывать ради совпадения с итоговым деревом; отдельный финальный manifest и перечень тестов именно на финальном snapshot. До локального commit проверить полный staged diff/`--check`, перечень файлов, staged blob content SHA-256 и manifest; после commit — exact committed blobs и manifest, не путать SHA-256 содержимого с Git OID. При CRLF→LF доказать ограниченность байтового преобразования, не менять общий Git config/.gitattributes/whitespace rules ради прохождения; исторический тест остаётся историческим, повтор функционального теста решать по объёму реального изменения, а не выдавать как состоявшийся.

Reviewer читает diff и доступное evidence и сообщает отдельно code review, независимо подтверждённый functional rerun и visual inspection: для каждого точный snapshot, среда, метод, исполнитель, PASS/CHANGES REQUIRED/UNVERIFIED. Нельзя называть запуск самого Programmer независимым. Визуальный PASS требует фактического просмотра пикселей/UI уполномоченным человеком/средством; PNG metadata или computed CSS не заменяют этого. Для кликабельности координатный ввод/hit-test, не только DOM `.click()`. Если изображение нельзя открыть — visual UNVERIFIED. Для краткого race/stale-modal эффекта на synthetic данных нужны две различимые даты, rapid switch, задержки/sequence с отметками, DOM/скрины/видео и запросы/ответы; финальный статический PNG недостаточен, отрицательное воспроизведение описать с условиями и числом попыток. Изменения app ради этого — только по scope отдельной задачи. Reviewer может дать read-only verdict/ссылки в разрешённом канале, но не создавать/менять файлы, Git state, БД либо external system; отсутствие назначенного независимого file-producing исполнителя не восполняется инструкцией.

## 6. Порядок работы, отказ и отчёт P09/P10
Lead формирует критерии и binding → поручает реализацию Programmer → получает diff и evidence → назначает независимую проверку доступными законными ролями → Reviewer оценивает ровно подтверждённые оси и выдаёт REVIEW ACCEPTED/CHANGES REQUIRED с ограничениями → Lead направляет rework в прежний scope и повторный Review затронутого финального snapshot → отчёт Owner с критериями, путями, SHA, результатами/UNVERIFIED, отказами и отсутствующими внешними gates. Ничего не публиковать/мержить/деплоить автоматически. Непроверенные production paths и rollback не становиться PASS. Если обнаружено расширение scope — остановка затронутой работы и новая Owner граница; прочие независимые этапы могут продолжаться.

## 7. Применение постоянных инструкций P10
До любой записи в пять живых целей подготовить полные окончательные байты нового регламента и четырёх SOUL, их точные SHA-256 и единый diff с контекстом и путями целей; все четыре SOUL уже содержат один и тот же окончательный path/version/hash регламента, без placeholder и последующей подстановки. Независимый Reviewer проверяет именно этот финальный пятицелевой пакет, исходные и итоговые хеши, binding и порядок применения **до** записи в любую живую цель. Изменение текста, пути или хеша после Review требует нового пакета и повторного независимого Review до применения. Принятие Review и подготовительный START сами по себе не разрешают применение. Только после отдельного явного Owner gate на точные пять целей/хешей, backup и уполномоченного совместимого исполнителя: заново прочитать исходные байты всех четырёх SOUL и старого регламента, сверить их хеши и отсутствие новой цели/конкурентных изменений, сохранить адресные backup существующих целей (имена/хеши, без раскрытия секретов). При drift, коллизии либо несовместимом доступе остановиться и вернуть пакет на Owner/Review. Исполнитель применяет только уже проверенные окончательные байты: staged/atomic замена где доступна, проверка точного SHA-256 регламента перед записью SOUL и адресный read-back SHA-256 каждой записанной цели и четырёх ссылок. Не генерировать новый diff и не подменять текст после Review. Частичная либо неоднозначная запись = UNKNOWN: остановиться, сохранить evidence, адресно прочитать фактическое состояние, без слепого повтора или rollback. Никакой файл/backup не удалять без отдельного разрешения. Текущий Kanban-текст не является применением.

## 9. Условный пилот одной постановки
Owner *в будущем* одним заявлением разрешает START небольшой **новой** локальной задачи, pilot dispatch, конкретный root/base SHA/allowed paths и при необходимости делегирует назначение отдельного worktree/branch по §2; одновременно запрещает production/external writes. После проверки актуальных условий и ролей Lead без последующих подсказок готовит матрицу критериев, назначает уникальный binding и роли; Programmer сверяет и выполняет local scope, сохраняет сырой evidence; отдельный допущенный не-implementer делает file-producing rerun если он требуется и доступен; Reviewer только читает и даёт три ограниченных вывода. Lead направляет исправления и отчёт Owner без push/PR/ready/merge/deploy/rollback/close/cleanup. Пилот успешен организационно, если не приходится повторно спрашивать Owner о штатных локальных шагах, а каждый настоящий запрос помечен как новая продуктовая неопределённость, новое право или реальный блокер. Отсутствующая модальность UNVERIFIED. Эта иллюстрация НЕ START и НЕ выдаёт прав на новую Issue.

## 10. Матрица предложения v1.3 (действует только после отдельного принятия Owner)
Эта версия и четыре SOUL применяются только после отдельного Owner gate на точные пять целей/хешей и независимого Review финальных байтов. Более строгие действующие Owner, developer, SOUL и tool boundaries имеют приоритет; текст не создаёт технический доступ и не удостоверяет роли.

Действие | Граница
--- | ---
Локальная разработка и тесты | Только внутри Owner START, binding и allowed paths отдельного worktree. Reviewer и Architect read-only, Lead не пишет проект и не проводит независимый Review.
Локальный commit | Только если прямо назван в START или отдельном Owner gate, после staged diff/hash/check; не означает push.
Push / draft PR / ready PR | Каждый названный внешний этап требует применимого Owner разрешения и точного read-back remote состояния. Независимый Review до публикации, если предписан данным gate. Принятие этого пакета не является разрешением на публикацию.
Clean local main fast-forward | Не выполняется Lead (developer запрещает проектные файлы) и Programmer (текущий feature-worktree-only boundary запрещает main). Только отдельный совместимый уполномоченный оператор после Owner gate с repository, ref, expected SHA, clean status, origin и ancestry; никакого reset/force/shared-config. Пока оператора нет — UNVERIFIED/NO-GO.
Task-owned disposable Docker | Только после явного START с локальными isolated resources, synthetic data, lifecycle и адресным cleanup. Никаких production volumes/compose/credentials; отказ в доступе к ресурсу не обходить.
Подготовка/тест миграции | Разрешённые файлы и одноразовые локальные данные при START; forward/rollback plan и тестовые evidence. Это не разрешает production DB write.
Production migration | Только внутри отдельного Owner DEPLOY с точным target, backup, data-preservation проверкой, steps и допущенным production оператором. Programmer напрямую production не меняет. Read-back/smoke; deploy не означает rollback.
Rollback | Отдельный Owner gate с целью и процедурой либо действительно заранее одобренная применимая emergency процедура. При UNKNOWN — stop/read-back, не повторять вслепую.
Restore / удаление данных / изменение доступа | Каждое требует отдельного адресного Owner gate, квалифицированного оператора и read-back. Не вытекает из START, DEPLOY, ROLLBACK или cleanup.
Функциональная/визуальная приёмка | Owner задаёт сценарий и среду. Reviewer отдельно сообщает code, независимый functional rerun и фактический visual inspection с snapshot, исполнителем, методом и PASS/CHANGES REQUIRED/UNVERIFIED. Недоступная ось — UNVERIFIED; собственный тест Programmer не независим.
MERGE / CLOSE / cleanup | Отдельные Owner MERGE и CLOSE, отдельный адресный gate для удаления ветки/worktree/evidence/backup.

Protected Coordination Card opt-in и N-06 affected egress остаются NO-GO; R02 T01–T10 не одобрены. Только фактически уполномоченный Global Lead может писать обычную каноническую Coordination Card. Global Lead/Tester не верифицированы как operational roles; runtime enforcement NO-GO/UNVERIFIED, IP conformance UNVERIFIED. Отказ локального метода записать буквально и продолжать только независимо разрешённые действия; запрет ресурса не обходить. Неоднозначная внешняя запись = UNKNOWN: stop и адресный read-back.

Конец полного проекта. Источники: реестр P01–P16 и live SOUL, указанные в комментарии 49. v1.1 комментарии 41–47 и оговорка прежнего проекта о приоритете §§3/7 только для рассмотрения остаются историческим происхождением до принятия. После отдельного Owner принятия точного пятицелевого пакета и разрешённого применения §§3/7 действуют лишь в пределах Owner scope и не отменяют более строгие developer, SOUL, tool и иные действующие ограничения; принятие не даёт START, доступа или права на внешние действия.
